零拷贝 vs 非零拷贝

场景：C# 手里有一块 4 MB 的 byte[]（引擎里最常见的形态：纹理 / 帧数据 / 顶点）， JS 要读它。把这份数据交到 JS 手上，有两条路：

零拷贝 —— GCHandle 钉住数组，把「地址 + 长度」交给 JS， JS 用公开 API runtime.localHeapViewU8().buffer 建出指向同一块内存的视图，零 memcpy；
非零拷贝 —— C# 把 Span<byte> 传过去（运行时封送成 MemoryView）， JS 用 copyTo（拷进复用缓冲）或 slice()（每次新分配一份），一次 memcpy。

为什么只测一个体积档

早先是 4 KB → 4 MB 四档，结果小档完全没法看：每次调用都在 JS 侧 new 一个视图， 几千次下来喂给 V8 的新生代回收，抖动比要测的差异还大好几倍 —— 4 KB 档两行相差 200 ns，抖动却是 2500～4150 ns，根本分辨不出来。 而「拷贝成本随体积线性增长」属于 memcpy 的物理性质（它是 O(n) 的），本就不必靠多档去验证。 所以只留一个大档：差异远超噪声、JS 垃圾也少，一次测干净。 「多大的数据才值得」改由页末的临界体积直接回答。

八条路线

①② 基线：C# 自己读（不跨界）、空跨界调用（过一次界的底噪），用来把共同成本扣掉；
③④⑤ 零拷贝：每次建视图 / 缓存视图（指针不变就复用，零分配）/ 每次都 pin；
⑥⑦ 非零拷贝：copyTo（拷进复用缓冲）、slice()（每次新分配）；
⑧ 基线：JS 内部 dst.set(src)，量出 memcpy 本身的价钱。

两个讲究：其一，各路线在 JS 侧只读首末各一个字节（O(1)）—— 若改成整块求和，那个 O(n) 的 JS 循环会把 memcpy 的 O(n) 成本完全淹没，几条路线会测出几乎一样快； 其二，每行都会对账校验值，读到的数据不对会在说明里标出来。
